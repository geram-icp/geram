# GERAM Ecosystem

Executive Introduction and Ecosystem Overview

A Strategic, Technical and Financial Infrastructure for Real-World Assets, Digital Identity, Tokenization and Intelligent Finance

---

1. Executive Summary

GERAM is designed as a comprehensive technology and financial ecosystem for transforming verified real-world assets, rights, projects, certificates, energy savings and other eligible economic resources into traceable, verifiable, governable and finance-ready digital representations.

The GERAM ecosystem combines:

- Real-World Asset (RWA) registration and verification
- Digital certificates and evidence management
- Asset valuation and risk assessment
- Collateralization and financial linkage
- Tokenization and digital asset infrastructure
- Digital identity and unified financial accounts
- Funds, credit, lending, borrowing and liquidity
- Marketplaces, DEX, OTC and settlement infrastructure
- Institutional finance and capital-market integration
- AI-assisted analysis and decision support
- Wallet and custody infrastructure
- Multi-currency and cross-border financial rails
- Governance, compliance, security and auditability
- Energy Measurement, Reporting and Verification (MRV)
- International and institutional interoperability

GERAM is therefore not intended to be merely an NFT platform, a token platform, a wallet, a marketplace or a lending application.

It is designed as a multi-domain financial and asset infrastructure in which each major domain has a clearly defined responsibility, source of truth, authority boundary and lifecycle.

At the center of this ecosystem are three complementary pillars:

GERAM

The Real-World Asset and Asset Finance Infrastructure.

NFID

The Identity, Account and Unified Financial Operating Interface.

HamiFund

The Fund, Credit, Lending, Liquidity and Intelligent Finance Infrastructure.

Together:

«GERAM establishes the trusted asset layer.
NFID establishes the trusted user and account layer.
HamiFund establishes the financial utilization layer.»

These three pillars are supported by a common platform consisting of identity, permissions, policies, wallets, tokenization, markets, oracles, valuation, risk, security, compliance, APIs, data, events, governance, financial rails and operational infrastructure.

2. The Core Vision

The fundamental problem addressed by GERAM is the separation that traditionally exists between:

- a real-world asset,
- its legal and documentary evidence,
- its valuation,
- its ownership or economic rights,
- its digital representation,
- its collateral value,
- its financing potential,
- and the financial markets through which capital can reach it.

GERAM is designed to create a controlled technological chain between these layers.

The conceptual model is:

Real-World Asset

→ Evidence

→ Verification

→ Rights / Economic Relationship

→ GERAM Asset

→ Certificate

→ Valuation

→ Collateral / Financial Link

→ Tokenization where permitted

→ Market / Fund / Financing

→ Settlement

→ Reconciliation

→ Audit

This architecture does not assume that every asset must become a token.

Instead:

«Tokenization is an optional representation layer applied only when eligibility, authorization, legal basis, economic mapping and policy requirements are satisfied.»

3. What GERAM Is

GERAM stands for:

Green Energy & Resource Asset Mechanism

Within the ecosystem, GERAM represents a protocol and infrastructure layer for registering, verifying, valuing, representing and financially utilizing eligible real-world assets and resource-based economic value.

GERAM provides the infrastructure required to answer questions such as:

- What is the underlying asset?
- Who or what entity is associated with it?
- What evidence supports it?
- Has the evidence been verified?
- What rights or economic relationships exist?
- What is its GERAM-ID?
- What certificate represents the verified record?
- What is its current valuation?
- Is it eligible for tokenization?
- Is it pledged or encumbered?
- Is it already being used as collateral?
- Is it connected to a financial product?
- Can it be transferred, financed or settled?
- What events have occurred during its lifecycle?
- Which institution or domain has authority over each state?

GERAM therefore acts as a trusted asset infrastructure, not simply a token issuance mechanism.

4. The GERAM Asset Model

A GERAM Asset is a structured and governed digital representation of an eligible real-world asset, right, project, certificate, resource or economic relationship.

The GERAM Asset model separates concepts that must not be confused:

Real-World Asset

is not automatically:

GERAM Asset

and a GERAM Asset is not automatically:

NFT

and an NFT is not automatically:

Financial Product

and a token is not automatically:

Legal Ownership

Each relationship must be explicitly defined, verified and governed.

This separation is one of the fundamental safeguards of the GERAM ecosystem.

5. GERAM-ID — The Asset Identity Layer

Every GERAM Asset receives a persistent:

GERAM-ID

GERAM-ID is intended to provide a stable identity for the asset record across its lifecycle.

It is distinct from:

- Token-ID
- NFT-ID
- Certificate-ID
- Wallet Address
- Principal
- Transaction ID
- Financial Account ID
- Project ID
- Equipment ID

This allows the underlying asset record to remain traceable even when its digital representation, ownership reference, financial status or tokenization state changes.

The principle is:

«Representation may change; asset identity remains traceable.»

10. NFID Is Not a Master Database

NFID must not become a centralized replacement for all domain registries.

For example:

GERAM remains authoritative for GERAM Asset state.

HamiFund remains authoritative for Fund, Credit and Loan state.

Token Factory remains authoritative for token definitions and tokenization infrastructure.

Settlement remains authoritative for settlement state.

Accounting remains authoritative for accounting records.

NFID can aggregate, present and orchestrate these states through a unified account and portfolio experience.

This is essential for scalability, security, domain sovereignty and long-term maintainability.

The participant authenticates through NFID.

The financial consequence is recorded.

The system confirms that all required records agree.

Step 15 — Audit

The complete lifecycle remains traceable.

## Overview

This project consists of two canisters:

- [backend](./backend/): a motoko canister with its [`backend.did`](./backend/backend.did) file.
- [frontend](./frontend/): a react webapp deployed in an asset canister.

### Bindings Generation

The [`@icp-sdk/bindgen`](https://npmjs.com/package/@icp-sdk/bindgen) library offers a plugin for Vite that generates the TypeScript Candid bindings from the [`backend.did`](./backend/backend.did) file. The bindings are generated at build time by Vite and are saved in the [`frontend/app/src/backend/api/`](./frontend/app/src/backend/api/) folder.

The plugin supports hot module replacement, so you can run the frontend in development mode (by running `npm run dev` in the [`frontend/app/`](./frontend/app/) folder) and make changes to the Candid declaration file to see the bindings being updated in real time.

See the [`vite.config.ts`](./frontend/app/vite.config.ts) file for how the plugin is used.

### Environment Variables

The project is configured to pass the backend's canister ID to the frontend using a [cookie](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Cookies). The environment variables are made available to the frontend JS code that runs in the browser by following this flow:

1. During deployment, the `icp` CLI sets the backend's canister ID in the frontend canister's (asset canister) environment variables
2. The asset canister sets a specific cookie (named `ic_env`) that contains some environment variables when the assets are uploaded
3. The asset canister serves the frontend assets with the cookie set
4. The frontend JS code uses the [`@icp-sdk/core/agent/canister-env`](https://js.icp.build/core/latest/canister-environment/) module to parse the cookie and extract the environment variables

In the [`App.tsx`](./frontend/app/src/App.tsx) file, you can see how the frontend can obtain the backend's canister ID from the environment variables and use it to create an actor for the backend canister.

## Run It

First, start a local network:

```bash
icp network start -d
```

Then, deploy both canisters:

```bash
icp deploy
```

This command will output something like this:

```
Syncing canisters:
[backend] ✔ Synced successfully: uqqxf-5h777-77774-qaaaa-cai
[frontend] ✔ Synced successfully: uxrrr-q7777-77774-qaaaq-cai # <- copy this canister id
```

Open the deployed frontend in a browser. Copy the frontend's canister ID from the output of the `icp deploy` command and construct the URL in this way: `http://<frontend_canister_id>.localhost:8000/`.

You can also make direct calls to the backend canister:
```bash
icp canister call backend greet '("Internet Computer")'
```

Finally, you can stop the local network with:

```bash
icp network stop
```
